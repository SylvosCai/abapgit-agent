# SO10 Standard Texts — AI Guidelines

SO10 standard texts are SAPscript content, not ABAP repository objects. Use `abapgit-agent so10` rather than `pull` or `customize` to manage them.

> **Never modify real texts, source baselines or CTS entries without explicit execution authorization.** Examples and isolated tests do not authorize live operations or named-text tests.

**Searchable keywords**: SO10, SAPscript, standard text, ITF, import, update, copy, transport, drop, baseline, conflict

---

## Identity and Configuration

A text is identified by its data client and full key:

| Field | Rule |
|---|---|
| Object | `TEXT` |
| Text name | Case-preserved, up to 70 characters |
| Text ID | Up to 4 characters; default `ST` |
| Language | One-character SAP key; CLI also accepts ISO language codes such as `EN` |

Track the following in the **application repository's** `.abapgit-agent.json`:

```json
{
  "so10": {
    "repoId": "example.app",
    "folder": "texts/so10"
  }
}
```

- Keep `repoId` stable: 1–80 lowercase ASCII letters, digits, `.`, `_` or `-`, starting with a letter or digit. Do not rename it to bypass ownership.
- Keep the managed folder inside the repository; symlinks are rejected.
- Store credentials only in ignored `.abapGitAgent`, never in the tracked file.

**Managed ITF file** (`.itf.json`):

```json
{
  "version": 1,
  "key": {
    "object": "TEXT",
    "name": "ZAPP_FOOTER",
    "id": "ST",
    "language": "E"
  },
  "lines": [
    { "tdformat": "*", "tdline": "Application footer" }
  ]
}
```

Preserve line order, formatting and whitespace. `tdformat` allows up to 2 characters and `tdline` up to 132. Empty or all-blank content, control characters, malformed UTF-8, unknown properties, duplicate keys and mismatched identities are rejected.

Let IMPORT or explicit file preparation generate the canonical full-key filename; do not guess it. Keep real text payloads in the application repository, not the tooling repository.

## Import and Update

```bash
abapgit-agent so10 list --prefix ZAPP_ --prefix ZOTHER_ --json
abapgit-agent so10 import --prefix ZAPP_ --language EN --dry-run --json
abapgit-agent so10 import --prefix ZAPP_ --language EN --json
# Edit the imported .itf.json, then update SAP:
abapgit-agent so10 update ZAPP_FOOTER --language EN --json
```

**Import rules:**
- Supply literal prefixes explicitly. Repeated prefixes are combined and full keys deduplicated; configuration is not a missing-argument fallback.
- The default limit is 100 texts; `--max-hits` accepts 1–1000. Overflow fails before reading bodies or writing files/baselines. Narrow the prefixes or choose a bounded limit.
- LIST and IMPORT `--dry-run` return headers only. READ and LIST never enroll a text.
- IMPORT validates the observed source and adopts it under its lock. It does not save SAP content, commit/push Git or create a transport entry.
- Dirty or untracked differing files are preserved. `--adopt-system` replaces only tracked, clean differing files; identical content stays byte-identical.
- A failed batch stops and reports earlier completed results. Local file rechecks do not prevent every race with an external editor.

**Update rules:**
- By default, managed UPDATE requires a baseline owned by this repository, even when the SAP content is identical.
- SHA-256 of canonical ITF lines detects divergence, including SAP GUI edits by the same user. User/date/time fields are diagnostics, not conflict proof.
- Explicit `--conflict-mode ignore` permits a missing baseline or source divergence, but never bypasses another repository's ownership, authorization, client policy, locks or validation.

## Create and Explicit Input

```bash
abapgit-agent so10 create ZAPP_FOOTER --language EN --itf-file drafts/footer.itf.json --json
abapgit-agent so10 update ZAPP_FOOTER --language EN --itf-file drafts/footer.itf.json --json
```

In an enabled repository, explicit input prepares the managed file without overwriting the external original or dirty work. Without an explicit input file, CREATE/UPDATE reads the managed full-key file.

Without enabled SO10 configuration, an explicit file and `--conflict-mode ignore` are required. These standalone writes do not advance Git baselines. CREATE fails if the text already exists, even if identical; UPDATE fails if it is missing.

**Check outcomes separately:** `saved` and `baseline_recorded` can be `true`, `false` or `null` (unknown); `file_written` is boolean. If a first CREATE saves content without a verified baseline, recover through explicit IMPORT, not another CREATE. Do not blindly retry unknown persistence. An owned, idempotent UPDATE can repair metadata without saving content again.

## Copy Between Clients

```bash
# Configured development client to customizingClient:
abapgit-agent so10 copy ZAPP_FOOTER --language EN --json
# Explicit clients, including a reverse correction:
abapgit-agent so10 copy ZAPP_FOOTER --language EN \
  --source-client "$SOURCE_CLIENT" --target-client "$TARGET_CLIENT" --overwrite --json
```

- COPY uses the unchanged development HTTP connection and selected backend data clients. Source defaults to the configured client; target defaults to `customizingClient`, then the configured client. Resolved clients must differ.
- The backend authorizes both clients, locks the target key and verifies the saved content. It does not flush another client's text catalog.
- COPY preserves the full text key and uses no local files or Git baselines. After a reverse correction, explicitly IMPORT if Git should adopt it.

## Record a Customizing Transport

```bash
abapgit-agent so10 transport ZAPP_FOOTER --language EN --transport "$CUSTOMIZING_TASK" --json
```

TRANSPORT is separate from COPY. Its logon client is selected from `--target-client`, `customizingClient`, then the configured client.

- A different client requires matching `customizingLogon.client`, `user` and `password` in ignored `.abapGitAgent`. Never clone development credentials into another client.
- Resolve the logon profile before looking up a task or making a request.
- Select an existing customizing task: explicit option, effective profile transport, environment, then existing-task selection. Do not fall back to a development task for another client.
- TRANSPORT records the exact `R3TR TEXT` key and returns the request/task. It does not create/release/import transports, copy content or guarantee a text snapshot; there is no `E071K` fallback.

## Git-Protected Drop

```bash
# Commit the managed ITF file and SO10 configuration before dropping:
abapgit-agent so10 drop ZAPP_FOOTER --language EN --json
abapgit-agent so10 drop ZAPP_FOOTER --language EN --target-client "$TARGET_CLIENT" --json
```

DROP defaults to the configured data client, not `customizingClient`, and retains the HTTP connection and Git files.

**Before deletion:**
1. Require clean, committed configuration and the full-key ITF payload at pinned HEAD. Staged, untracked or dirty files, changed HEAD/configuration and duplicate keys fail.
2. Under the selected full-key lock, check native SHOW/EDIT authorization, client policy and the repository-owned baseline.
3. Require both the current SAP content and baseline to match the committed ITF payload.

The backend deletes the exact text through native `DELETE_TEXT`, verifies absence, then removes only the matching owned baseline. Never write STXH/STXL directly, save an empty text or flush another client's catalog.

A copied target has no Git baseline: explicitly IMPORT it and commit the payload before DROP. There is no standalone mode, external payload, conflict-ignore, overwrite, source-client, transport or `delete` alias.

**Check outcomes separately:** `deleted` and `baseline_removed` can be `true`, `false` or `null`; `saved` remains `false`. Verified absence can recover an earlier deletion only while its matching owned baseline remains. Metadata-cleanup failure does not undo deletion; do not blindly retry unknown outcomes.

## Limitations

- No package activation, mass copy, cross-system RFC, INCLUDE/style/form dependency copying or deployment pipeline.
- Isolated tests do not prove live authorization, independent-session durability or CTS roundtrips. Named-text tests need their own execution authorization.
